\chapter{Discussion}
\label{ch:discussion}

The empirical evaluation presented in Chapter~\ref{ch:evaluation_results}
answered the four research questions guiding this study, demonstrating the
feasibility, structural concordance, and computational scalability of OmniDeps
across 156 real-world software repositories and five programming languages.
However, interpreting these quantitative findings requires stepping
back from raw
similarity metrics and runtime curves to examine the broader architectural,
methodological, and practical implications of a language-agnostic
approach to static
analysis.

This chapter synthesizes the empirical outcomes into a discussion
structured around four primary themes:
\begin{enumerate}
  \item \textbf{Empirical Findings Across Paradigms}: We examine how
    syntax-directed dependency extraction interacts with different type systems
    and compilation models across object-oriented, dynamic, procedural, and
    systems programming languages.
  \item \textbf{Efficacy of the Language-Agnostic Approach}:\ We evaluate
    the\linebreak
    trade-offs between decoupling the analyzer from native build toolchains and
    relying on compiler-coupled semantic resolution.
  \item \textbf{Practical Implications}: We discuss how software engineering
    practitioners and tool authors can integrate fast, language-agnostic
    dependency extraction into continuous integration workflows and downstream
    architectural smell detectors.
  \item \textbf{Threats to Validity}: We analyze the construct, internal, and
    external limitations that bound the interpretation and generalizability of
    our results.
\end{enumerate}

\section{Empirical Findings Across Paradigms}
\label{sec:discussion_findings}

Our empirical findings uncover fundamental differences in how programming
language paradigms interact with syntax-directed static dependency extraction.
Rather than reflecting uniform performance across the dataset, the results
highlight distinct extraction dynamics across object-oriented, dynamic,
procedural, and modern systems languages.

\subsection{Object-Oriented Parity in Java}
\label{subsec:discussion_oo_parity}

The most prominent empirical finding in object-oriented environments is the
near-complete convergence of architectural entities and the high degree of
relational concordance between OmniDeps and compiler-backed analyzers. As
reported in Section~\ref{subsec:results_rq2}, OmniDeps exhibited negligible
entity omission against both Depends and Arcan, while achieving consistent
edge similarity across all three baseline tools.

This convergence validates a foundational architectural hypothesis: in
explicitly typed, modular object-oriented languages, Concrete Syntax Trees
contain virtually all structural information required for architectural
dependency modeling. In Java, source code maps directly to the
architectural structure:
\begin{itemize}[noitemsep]
  \item Source files map cleanly to canonical package hierarchies via explicit
    package declarations.
  \item Structured types such as classes, interfaces, enums, and records are
    explicitly declared together with their subtyping relations.
  \item Dependency targets are explicitly imported via import statements or
    qualified inline references.
\end{itemize}

Because compilation units in Java cannot inject arbitrary global preprocessor
macros or alias global namespaces dynamically, OmniDeps' two-phase algebraic
query model resolves nearly all compiler-identified architectural entities
without requiring access to external binary dependencies or a live Java Virtual
Machine.

As shown in Section~\ref{subsec:results_rq3}, containment relationships agree
almost completely across tools. The remaining edge differences come from
different extraction boundaries for usage dependencies rather than missing
entities, confirming that syntax queries achieve accuracy comparable to
compiler-based tools.

\subsection{Resolution Limits in Dynamic Languages}
\label{subsec:discussion_dynamic_languages}

In contrast to object-oriented environments, evaluating Python codebases
dem\-on\-strates how graph harmonization reconciles divergent extraction scopes
in dynamic ecosystems: while entity identification attains high concordance
($J_{\text{nodes}} = 0.852$) with an entity omission rate of just $4.8\%$,
call-level dependency alignment achieves $J_{\text{edges}} = 0.323$, rising to
$0.368$ when isolating behavioral relations from unmodeled syntactic imports.
Comparing the extracted graphs shows that two main factors explain these
results: the limits of dynamic typing for method calls, and how method-local
test fixtures are handled at the entity level.

\paragraph{Dynamic Typing and Call Divergence.}
The moderate edge similarity reflects the limits of syntax-only static
analysis in dynamically typed languages. In Python:
\begin{itemize}
  \item \textbf{Absence of Static Type Annotations}: In idiomatic Python
    codebases, function arguments and local variables frequently omit type
    signatures. Without runtime information or expensive data-flow analysis,
    a syntax-only analyzer cannot determine the concrete type of an
    unannotated parameter.
  \item \textbf{Late Binding and Duck Typing}: Method invocations are
    dispatched dynamically by attribute name lookup rather than static virtual
    method tables.
\end{itemize}
While OmniDeps leverages static type annotations \cite{pep484} whenever present
in function signatures and variable declarations, real-world Python
repositories in the dataset adopt type annotations only partially or
inconsistently \cite{magalhaes_understanding_2026}. In unannotated
code, both OmniDeps and Depends inevitably arrive at divergent
heuristics when resolving ambiguous method calls, naturally bounding
edge Jaccard agreement to $\approx 0.30$--$0.33$.

\paragraph{Node Disparity and Method-Local Closures.}
At the entity tier, an initial unharmonized comparison indicated substantial
node discrepancies on several test-heavy repositories, such as
\texttt{sqlalchemy} ($J_{\text{nodes}} = 0.485$), \texttt{marshmallow}
($0.339$), and \texttt{pydantic} ($0.234$). A structural inspection of the
discordant entity sets revealed the exact methodological root cause: a
fundamental scope disagreement concerning \textbf{method-local classes} within
unit test suites. In Python testing frameworks, test cases extensively declare
throwaway mock models and schemas directly inside individual test functions.
Depends extracts all classes found in the AST, treating classes declared
inside test functions as regular architectural types. Empirical
quantification across the extracted graphs revealed that method-local classes
accounted for \textbf{70.9\%} of all types extracted by Depends in Pydantic,
\textbf{54.3\%} in SQLAlchemy, and \textbf{61.2\%} in Marshmallow.

In contrast, OmniDeps extracts types only at module and class scope, ignoring
method-local classes because test mocks have no visibility outside their
enclosing function.

When the graph harmonization adapter applies Semantic Entity Lifting
(Section~\ref{subsec:semantic_lifting}) to classify method-local classes as
volatile entities and lift their external references to the enclosing class or
module, entity agreement realigns across the dataset:
\begin{itemize}
  \item In \texttt{sqlalchemy}, node Jaccard similarity rises from $0.485$ to
    \textbf{0.946}, while node inferiority drops from $1.030$ to \textbf{0.024}.
  \item In \texttt{marshmallow}, node Jaccard increases from $0.339$ to
    \textbf{0.782}, with node inferiority dropping from $1.683$ to
    \textbf{0.005}.
  \item Across all 29 evaluated Python repositories, mean node Jaccard improves
    from $0.740$ to \textbf{0.852}, and mean entity omission drops by
    \textbf{85.5\%}, from $0.332$ down to \textbf{0.048}.
\end{itemize}
This confirms that OmniDeps captures over 95\% of architectural entities in
Python, showing that the initial gap was caused by test-local classes rather than
missing application code.

\paragraph{Edge Superiority and Import Asymmetry.}
A notable characteristic of the comparative edge metrics on Python repositories
is the elevated edge superiority ($\text{Sup}_{\text{edges}} = 1.474$ mean),
indicating that OmniDeps extracts considerably more edges than Depends.
Comparing the edge differences reveals three main reasons for these extra
edges:
\begin{itemize}
  \item \textbf{Syntactic Import Asymmetry}: The largest single component of
    edges unique to OmniDeps is syntactic module inclusion. OmniDeps extracts
    every explicit import statement as a first-class \texttt{includes} edge,
    such as 18,494 in \texttt{sympy} and 5,982 in \texttt{scikit-learn}. In
    contrast, Depends Python bypasses file-level import statements almost
    entirely, generating only 47 \texttt{includes} edges in \texttt{sympy} and
    22 in \texttt{scikit-learn}. Because the global edge Jaccard metric pools
    all relation categories into a single unweighted set, this categorical
    asymmetry accounts for over half of all edges unique to OmniDeps in large
    scientific libraries.
  \item \textbf{High-Fidelity Cross-Module Inheritance Resolution}: In
    subtyping hierarchies (\texttt{isChildOf}), OmniDeps exhibits higher recall
    than Depends, identifying 1,041 inheritance arcs in \texttt{scikit-learn}
    compared to 491 in Depends. In large Python libraries, inheritance
    hierarchies frequently rely on relative module imports to compose mixins
    and base abstractions. Because these relative imports lack static type
    annotations, Depends treats them as ambiguous symbols and discards them,
    whereas OmniDeps deterministically resolves relative import paths across
    the file system using its hierarchical Scope Tree.
  \item \textbf{Language-Agnostic Polyglot Workspace Traversal}: Modern
    software projects are increasingly polyglot. While Depends Python parses
    only \texttt{.py} files within declared roots, OmniDeps recursively
    analyzes all source files matching any supported grammar across the
    repository work\-space. For instance, in \texttt{pydantic}, OmniDeps also
    parses the native Rust core, extracting its struct definitions, validators,
    and serializers, whereas single-language Python analyzers treat compiled
    extensions as opaque external binaries.
\end{itemize}
Thus, the higher edge count comes from broader syntactic coverage, relative
imports, and multi-language files, rather than false-positive dependencies.

\paragraph{Behavioral Concordance Without Imports.}
To verify that the aggregate edge metric is distorted by the unmodeled import
statements in Depends, we performed a controlled evaluation isolating purely
behavioral interactions (invocations, type usage, and inheritance) by excluding
syntactic \texttt{includes} edges across the Python dataset ($N = 29$).

Across all 29 repositories, the median edge Jaccard similarity increases from
$0.300$ to \textbf{0.387} (mean from $0.323$ to \textbf{0.368}), while the
median edge superiority index drops below parity to \textbf{0.889} (mean falls
from $1.474$ to \textbf{1.017}). The effect is particularly pronounced in large
libraries where OmniDeps captures extensive import graphs, such as
\texttt{scikit-learn} ($J_{\text{edges}}$ rising from $0.209$ to
\textbf{0.317}) and \texttt{django} ($\text{Sup}_{\text{edges}}$ dropping from
$1.584$ to \textbf{0.951}). This proves that when comparing purely behavioral
dependencies on an identical semantic plane, syntactic static analysis in
dynamically typed languages achieves nearly $40\%$ behavioral concordance with
compiler-grade analyzers. Table~\ref{tab:python_harmonization_ablation}

\subsection{Preprocessing and Headers in C and C++}
\label{subsec:discussion_procedural_dilemma}

The empirical evaluation of C and C++ repositories highlights a central
trade-off driven by two factors: macro expansion and header inlining.

\paragraph{Macro Masking in Raw Sources.}
In raw, unprocessed C and C++ source code, extensive use of preprocessor
macros fundamentally obscures the underlying syntax. Macros are routinely used
to declare function wrappers, synthesize struct typedefs, declare interface
dispatch tables, and implement conditional compilation. As shown in
Table~\ref{tab:results_summary_rq2}, analyzing raw C code produces a modest
edge Jaccard similarity of $0.115$. Tree-sitter parsers, encountering macro
invocations that do not conform to standard C grammar, frequently classify
complex macro statements as generic call expressions or syntax errors, causing
referenced structs and typedefs to remain unlinked.

\paragraph{Preprocessing vs. Header Duplication.}
When translation units are preprocessed via the compiler frontend, macros are
fully expanded, conditional directives are evaluated, and all included header
files are inlined directly into the source stream. As documented in
Section~\ref{subsec:results_rq2}, this produces a substantial boost in
structural recall: in C++, edge Jaccard agreement doubles from $0.081$ to
$0.165$ (reaching $0.459$ on \texttt{re2} and $0.320$ on \texttt{ninja}), while
node inferiority drops significantly. At the categorical level
(Section~\ref{subsec:results_rq3}), macro expansion resolves masked type
declarations and function signatures, cutting structural containment omission
in C++ nearly in half (from $93.5\%$ down to $47.4\%$) and substantially
reducing behavioral dependency omission (from $92.6\%$ to $67.8\%$).

However, preprocessing causes header duplication: inlining headers copies
standard library and shared project declarations into every file. Because each
preprocessed file is parsed as a self-contained translation unit, types
declared in shared headers are replicated across every module that includes
them. This replication inflates both node superiority
($\text{Sup}_{\text{nodes}} = 7.22$ in C and $4.91$ in C++) and the proportion
of edges unique to OmniDeps ($\Delta_{A \setminus B}$), as OmniDeps extracts
these duplicated and external declarations directly from each expanded syntax
tree.

\paragraph{System Headers and Enum Granularity.}
Looking closely at the node differences between OmniDeps and Depends reveals
three main causes:
\begin{itemize}
  \item \textbf{Standard Library and POSIX Header Inlining}: Under
    translation-unit preprocessing, the compiler inlines not only local project
    headers, but the entire POSIX and C runtime library, injecting standard
    system structs into every file. OmniDeps faithfully extracts every
    syntax-level struct definition from the CST, whereas Depends leverages
    Eclipse CDT's build-system configuration to filter out external system
    include paths.
  \item \textbf{Enum Variant Harmonization Granularity}: In C, enumerations are
    ubiquitous. In the graph harmonization model, OmniDeps preserves each
    individual enum variant as an architectural component. In contrast, Depends
    models enum constants as scalar variables, which the restricted
    harmonization filter prunes as volatile entities. In projects like
    \texttt{redis}, this granularity difference alone accounts for roughly half
    of the entire node divergence (673 out of 1,343 nodes missing in Depends).
  \item \textbf{Vendored Directory Traversal}: While build-system-coupled
    analyzers restrict extraction to targets declared in primary build scripts,
    OmniDeps performs a recursive workspace walk, parsing vendored dependencies
    nested in subdirectories (such as bundled \texttt{jemalloc} and
    \texttt{lua} sources in \texttt{redis}) as well as anonymous typedefs.
\end{itemize}
Crucially, despite this large set of additional nodes, entity omission remains
low ($\text{Inf}_{\text{nodes}} = 0.057$ on \texttt{git}, $0.202$ on
\texttt{redis}, and $0.140$ on \texttt{curl}), confirming that OmniDeps
captures virtually all core entities extracted by Depends. The lower Jaccard
score is therefore due to duplicated header nodes inflating the denominator,
rather than missed project entities.

\paragraph{Incomplete Types in Header Stripping.}
To address this duplication, our exploratory investigation evaluated stripping
inlined header declarations using compiler linemarkers. However, this
experiment exposed a fatal flaw in compiler-dependent baseline tools: removing
header definitions leaves source files with incomplete forward type
declarations. While OmniDeps' query engine tolerates incomplete forward
declarations, compiler frontends such as Eclipse CDT within Depends require
complete struct layouts to resolve member offsets and pointer dereferences.
Consequently, CDT crashed with syntax and unresolved symbol exceptions across
nearly every stripped project, proving that compiler-based frontends cannot
function without complete header inlining.

These results show that in C and C++, files cannot be treated as isolated
modules. Handling headers accurately requires deduplicating identical struct
declarations across files after parsing, while preserving their dependencies.

\subsection{Modularity and Traits in Rust}
\label{subsec:discussion_rust_modularity}

The evaluation of Rust repositories provides an instructive counterpoint to C
and C++. Rust combines low-level systems programming performance with a modern,
strictly enforced modularity model:
\begin{itemize}[noitemsep]
  \item Module hierarchies map strictly to the filesystem hierarchy.
  \item Dependencies across crates and submodules are explicitly declared via
    canonical \texttt{use} paths.
  \item Behavioral polymorphism is governed by explicit trait implementation
    blocks rather than header files or preprocessor macros.
\end{itemize}

OmniDeps successfully analyzed 100\% of the 32 Rust repositories, sustaining a
throughput of over 97,000 LOC/s. Because Rust's grammar provides unambiguous
syntactic demarcations for struct definitions, enum variants, and trait
implementations, the algebraic query engine resolves cross-module type
references with high determinism. This confirms that modern systems languages
engineered with clean module systems allow CST-based static analysis to achieve
compiler-level fidelity while completely bypassing compiler toolchain overhead.

\section[Efficacy of the Language-Agnostic Approach]{Efficacy of the
Language-Agnostic\\Approach}
\label{sec:discussion_efficacy}

A central question guiding this thesis is whether developing a
language-agnostic, syntax-directed static analyzer is architecturally and
practically worthwhile compared to maintaining dedicated, compiler-coupled
frontends.

The empirical results show that this trade-off is well justified for
architectural analysis. While compiler-based tools offer deeper type resolution
in specialized cases like complex C++ templates, syntax-based analysis provides
three main practical advantages: reliability, speed, and maintainability.

\subsection{Decoupling from Build Systems}
\label{subsec:discussion_build_decoupling}

A key advantage of OmniDeps is its much higher completion rate compared to
tools coupled to build environments. Tools that integrate with compiler
frontends or build systems, such as Arcan and Entangle, require projects to be
configured and resolvable on the host machine. When applied to heterogeneous
open-source repositories, these prerequisites frequently fail due to missing
external dependencies, platform-specific configurations, uninitialized
submodules, or outdated build scripts, causing compiler-coupled tools to abort
on a large fraction of the benchmark corpus.

In contrast, OmniDeps operates under the assumption that \textbf{the analyzed
source code already compiles within its native environment}, decoupling static
analysis from build-system execution. Because it operates directly on raw
source files on disk without requiring external dependencies or build
configuration, OmniDeps completed analysis across almost the entire dataset.
For large-scale empirical studies or multi-language enterprise repositories,
extracting high-fidelity architectural dependencies with zero build setup
provides substantially higher practical reliability than relying on fragile
build pipelines.

\subsection{Precision Versus Scalability}
\label{subsec:discussion_precision_tradeoff}

Traditional compiler frontends dedicate significant computational resources to
whole-program semantic analysis, including control-flow construction,
interprocedural points-to resolution, and type checking. However, for
\textbf{architectural dependency analysis}, much of this verification is
redundant when the source code has already been validated by the developer's
toolchain.

OmniDeps replaces multi-pass compiler verification with single-pass CST
extraction followed by algebraic resolution over the Scope Tree. As shown in
Section~\ref{subsec:results_rq4}, this design enables the analyzer to process
large repositories in a few seconds, running one to two orders of magnitude
faster than compiler-backed baselines. At the same time, the comparative
evaluation in Java demonstrated that this speedup comes with minimal entity
omission. For macro-architectural analyses such as cyclic dependency detection
or component cohesion assessment, minor differences in fine-grained call edges
do not alter the recovered architectural topology, making the trade-off between
exhaustive type checking and high-throughput syntax analysis highly effective
in practice.

\subsection{Polyglot Extensibility}
\label{subsec:discussion_engineering_economy}

Building and maintaining a multi-language static analysis framework on top of
compiler frontends requires integrating separate, incompatible ecosystems for
each target language, such as Clang for C and C++ or Eclipse JDT for Java. Each
compiler API evolves independently, exposes a different internal syntax model,
and requires its own runtime environment and language-specific resolution
pipeline.

In contrast, OmniDeps maintains a single unified pipeline across all supported
languages. By relying on Tree-sitter for parsing, adding support for a new
programming language only requires defining its extraction heuristics and
scoping parameters in the configuration layer to map CST nodes into the
Intermediate Representation. The underlying algebraic query engine, Scope Tree
indexing, and graph synthesis stages remain completely unchanged and
language-independent, substantially reducing the engineering effort required to
support and maintain multiple languages.

\section{Practical Implications}
\label{sec:discussion_implications}

The findings of this thesis have direct practical implications for software
engineering workflows and architectural analysis tools.

\subsubsection{Continuous Integration Auditing}
\label{subsec:implications_ci_cd}

Traditional dependency auditing tools often run only in nightly batch jobs
because their execution times range from minutes to hours. Because OmniDeps
analyzes large codebases in seconds without requiring a build, it can run
directly in \textbf{continuous integration pipelines} and pre-commit checks.
Development teams can thus enforce architectural constraints, such as detecting
layer violations or cyclic component dependencies, during routine code review
before changes are merged.

\subsubsection{Universal Frontend for Smell Detectors}
\label{subsec:implications_smell_detection}

Architectural analysis platforms such as \textit{Arcan}
\cite{fontana_arcan_2017}, \textit{DV8} \cite{cai_dv8_2019}, and
\textit{SonarQube} invest considerable effort in developing and maintaining
language-specific parsers and extractors. OmniDeps' Intermediate
Representation
and normalized dependency graph exports can serve as a \textbf{universal
dependency extraction frontend} for these downstream tools, allowing
smell detectors to
extend their coverage across C, C++, Java, Python, and Rust without maintaining
separate compiler-coupled pipelines.

\subsubsection{Polyglot Monorepo Governance}
\label{subsec:implications_monorepos}

Modern software systems increasingly adopt polyglot repository
structures,\linebreak
where services, native extensions, and shared libraries written in different
languages coexist within a single workspace. While traditional analyzers
operate within single-language silos, OmniDeps projects components from all
supported languages into a single language-neutral Intermediate Representation
with canonical qualified naming, providing a unified foundation for inspecting
mul\-ti-lan\-guage repositories within a single dependency multigraph.

\section{Threats to Validity}
\label{sec:threats_to_validity}

We discuss the limitations of our study across construct, internal, and
external validity.

\subsubsection{Construct Validity}
\label{subsec:construct_validity}

Threats to construct validity concern whether the evaluation metrics and graph
transformations reflect genuine dependency extraction fidelity rather than
representation artifacts.

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Harmonization and Semantic Lifting}:
    To compare tools operating at different granularities, we lifted
    member-level interactions to their enclosing types and synthesized
    intermediate packages (Section~\ref{subsec:graph_harmonization}). While
    this enables a direct comparison, it focuses the evaluation on
    architectural dependencies rather than statement-level details.

  \item \textbf{Manual Catalogs of Primitive Types}:
    OmniDeps identifies built-in and primitive types through predefined,
    per-language catalogs in order to synthesize terminal primitive endpoints
    rather than attempting workspace symbol resolution. Although these catalogs
    were constructed from official language specifications across all five
    languages, maintaining manual lists introduces a risk that uncommon
    platform-specific aliases may remain unclassified and be treated as
    external symbols.

  \item \textbf{Granularity Mismatch in Procedural Languages}:
    In procedural C and C++, while OmniDeps and Depends extract user-defined
    types such as structs, unions, and classes, Arcan models dependencies
    primarily at the physical file and header level. Because intersecting
    file-level and type-level vertex sets produces an empty overlap that would
    falsely suggest zero extraction capability, we explicitly excluded Arcan
    from the C and C++ structural similarity comparison
    (Section~\ref{subsec:results_rq2}).

  \item \textbf{Polyglot Workspace Traversal vs. Single-Language Baselines}:
    Unlike baseline tools that restrict analysis to a single target language or
    build manifest, OmniDeps recursively parses all supported source files
    across a repository workspace. As examined in
    Section~\ref{subsec:results_rq2} and
    Section~\ref{subsec:discussion_dynamic_languages}, secondary languages
    embedded in polyglot repositories are extracted exclusively by OmniDeps,
    which systematically increases directional superiority metrics without
    indicating false-positive couplings.

  \item \textbf{Metric Sensitivity and Smoothing}:
    Standard Jaccard similarity becomes indeterminate on sparse subgraphs and
    cannot distinguish between under-approximation and over-approximation. To
    mitigate this, we combined Laplace-smoothed Jaccard formulations with
    directional superiority and inferiority indices
    (Section~\ref{subsec:comparative_metrics}) to evaluate extra and omitted
    elements independently.
\end{itemize}

\subsubsection{Internal Validity}
\label{subsec:internal_validity}

Threats to internal validity concern confounding factors in the experimental
setup, analysis pipeline, and measurement protocol that could bias the observed
results.

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{C and C++ Preprocessing Trade-offs}:
    As analyzed in Section~\ref{subsec:discussion_procedural_dilemma},
    evaluating C and C++ codebases involves an inherent trade-off between macro
    masking in raw source files and header replication in preprocessed
    translation units, while stripping inlined headers breaks compiler-coupled
    baselines due to incomplete forward types. To avoid biasing the evaluation
    toward a single operating point, we evaluated and reported both raw and
    preprocessed configurations side by side.

  \item \textbf{Unmodeled C-Style Variadic Functions}:
    OmniDeps does not explicitly model C-style variadic parameter lists in its
    intermediate representation. Because untyped variadic arguments do not
    introduce named type references in function signatures, no static type
    dependency edge is lost at the declaration site; however, concrete argument
    types passed at variadic call sites cannot be resolved statically without
    interprocedural data-flow analysis.

  \item \textbf{Dynamic Language Features and Reflection}:
    As discussed in Section~\ref{subsec:discussion_dynamic_languages}, purely
    syntactic static analysis cannot observe runtime reflection, dynamic
    attribute dispatch, or runtime symbol table mutation in dynamically typed
    languages such as Python. This represents an intrinsic ceiling on static
    call recall whenever type annotations are absent.

  \item \textbf{Runtime Measurement Variance and Execution Environment}:
    Comparing a native Rust binary against JVM-based analyzers such as Arcan
    and Depends introduces potential runtime differences due to virtual machine
    startup, just-in-time compilation, and garbage collection. To ensure a fair
    comparison, each repository was analyzed in an isolated process session
    under identical hardware constraints
    (Section~\ref{sec:performance_benchmarking}),
    and execution times were aggregated across multiple runs using both
    arithmetic means and medians to guard against outliers.
\end{itemize}

\subsubsection{External Validity}
\label{subsec:external_validity}

Threats to external validity concern the generalizability of our conclusions to
other programming paradigms and software systems.

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Generalizability Across Programming Paradigms}:
    Although our evaluation spans five languages, all five are imperative,
    procedural, or object-oriented. Our findings may not generalize directly to
    purely functional or declarative languages, where software structure is
    based on function composition or algebraic modules rather than types and
    call graphs.

  \item \textbf{Dataset Representativeness}:
    The 156 evaluated repositories were\linebreak sourced exclusively
    from open-source
    projects hosted on GitHub, which may not fully reflect proprietary
    enterprise codebases with unconventional layouts. To mitigate selection
    bias, the benchmark corpus was curated to span nearly 98 million lines of
    code across diverse domains, ranging from compact libraries to monolithic
    systems exceeding one million lines of code.
\end{itemize}
