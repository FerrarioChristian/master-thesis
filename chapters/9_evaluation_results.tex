\chapter{Evaluation and Validation Methodology}
\label{ch:evaluation_results}

Evaluating the effectiveness of a language-agnostic static analysis framework presents substantial empirical and methodological challenges. Unlike single-language analyzers whose outputs can be validated against compiler symbol tables or standardized language specifications, a universal dependency extractor must be assessed across fundamentally divergent programming paradigms, type systems, and modularity models. Furthermore, validating dependency graphs extracted from large-scale, real-world software systems requires objective ground-truth references, which are inherently difficult to obtain manually for systems comprising millions of lines of code.

To address these challenges, this chapter formalizes a rigorous, multi-faceted evaluation methodology. The validation strategy rests on two foundational pillars:
\begin{enumerate}
  \item \textbf{Ground-Truth Verification via Controlled Micro-Benchmarks}: Evaluating the absolute precision and recall of the extraction pipeline against hand-crafted semantic oracles designed to rigorously exercise complex language-specific corner cases (e.g., C++ template specializations, Java bounded type parameters, Rust trait implementation blocks, and Python dynamic re-exports).
  \item \textbf{Cross-Tool Structural Alignment and Scalability on Real-World Systems}: Benchmarking the proposed analyzer against established state-of-the-art static analysis tools (\textit{Arcan}, \textit{Depends}, and \textit{Entangle}) across a curated corpus of heterogeneous open-source repositories.
\end{enumerate}

To establish an objective basis for cross-tool comparison, this chapter introduces a formal \textbf{Graph Alignment and Harmonization Framework}. This framework resolves syntactic and metamodel mismatches across heterogeneous analyzers through canonical entity identification, semantic entity lifting, structural containment synthesis, and edge taxonomy unification.

\section{Research Questions}
\label{sec:research_questions}

The empirical and theoretical evaluation is guided by four central Research Questions (RQs):

\begin{itemize}[leftmargin=2.5em]
  \item[\textbf{RQ1}] \textbf{(Ground-Truth Extraction Fidelity)}: \\
    \textit{To what degree does the language-agnostic Intermediate Representation and query-based resolution engine accurately recover architectural entities and semantic dependencies when evaluated against formal, manually verified semantic oracles across heterogeneous programming languages?}
  
  \item[\textbf{RQ2}] \textbf{(Cross-Tool Structural Alignment)}: \\
    \textit{How closely do the dependency graphs extracted by OmniDeps align with the representations produced by established single-language and multi-language architectural analyzers on large-scale open-source software systems?}
  
  \item[\textbf{RQ3}] \textbf{(Typological Concordance and Discrepancy Analysis)}: \\
    \textit{In which specific categories of software dependencies (structural containment, inheritance hierarchies, behavioral invocations, module inclusion) do cross-tool discrepancies concentrate, and what semantic assumptions or architectural trade-offs account for observed divergences?}
  
  \item[\textbf{RQ4}] \textbf{(Computational Scalability and Throughput)}: \\
    \textit{How does the computational throughput and memory scaling of OmniDeps compare against state-of-the-art baselines when analyzing repositories of varying scale, from compact libraries to multi-million-line codebases?}
\end{itemize}

\section{The Graph Alignment and Harmonization Framework}
\label{sec:graph_harmonization_framework}

Directly comparing the dependency graphs emitted by independent static analysis tools is non-trivial. Different analyzers operate under distinct metamodels, graph schemas, serialization formats (e.g., GraphML, DSM JSON, Cytoscape JSON), and granularity assumptions. Without a formal alignment framework, naive graph intersections yield artificially low concordance metrics caused entirely by superficial representational differences rather than true semantic disagreements.

This section presents the formal mathematical model developed to harmonize heterogeneous dependency graphs into an isomorphic, canonical representation suitable for objective comparative evaluation.

\subsection{The Metamodel Heterogeneity Problem}
\label{subsec:metamodel_heterogeneity}

State-of-the-art analyzers conceptualize software structure at differing levels of abstraction:
\begin{itemize}
  \item \textbf{Granularity Divergence}: Fine-grained tools (such as \textit{Depends} \cite{depends_github} and \textit{Entangle} \cite{teruzzi_2024}) extract AST-level variables, functions, and method invocations as distinct graph vertices. Conversely, architectural analyzers (such as \textit{Arcan} \cite{fontana_arcan_2017}) focus primarily on coarse-grained structural components---specifically packages, classes, and interfaces in object-oriented environments (Java), and physical source/header compilation units in procedural codebases (C/C++).
  \item \textbf{Implicit vs. Explicit Structural Hierarchy}: Certain graph models represent modular containment through explicit directed edges (e.g., $\texttt{belongsTo}$ or $\texttt{ModuleContainment}$), whereas compound graph specifications (such as Cytoscape.js \cite{franz_cytoscapejs_2016}) represent hierarchy geometrically via node nesting attributes (\texttt{parent} pointers), omitting explicit containment edge primitives.
  \item \textbf{Relational Taxonomy Mismatch}: Each tool employs proprietary relationship vocabularies. For instance, a method invocation may be classified as \texttt{Calls} in one tool, \texttt{call} in another, or subsumed into a generic \texttt{dependsOn} relation in an architectural smell detector. Similarly, subtype relationships may be split into \texttt{extend} and \texttt{implement}, or unified as \texttt{isChildOf} or \texttt{IsA}.
  \item \textbf{Namespace and Identifier Disparities}: Differing path separators (\texttt{::} in C++/Rust, \texttt{/} in file paths, \texttt{.} in Java/Python), varying handling of nested anonymous scopes, and synthetic root prefixes prevent exact string matching of entity names.
\end{itemize}

To overcome these structural disparities, we define an algebraic transformation pipeline that normalizes any tool's extracted graph $G_{\text{raw}} = (V_{\text{raw}}, E_{\text{raw}})$ into a standardized architectural dependency graph $G_{\text{arch}} = (V_{\text{arch}}, E_{\text{arch}})$.

\subsection{Entity Canonicalization and Volatility Classification}
\label{subsec:entity_canonicalization}

Let $\mathcal{I}^*$ denote the set of raw identifier strings emitted by an analyzer. We define a canonical path normalization function $\mathcal{N} : \mathcal{I}^* \to \Pi$ that maps language-specific and tool-specific namespace separators to unified qualified paths $\pi \in \Pi$ (as formalized in Chapter \ref{ch:ir_formalization}):
\begin{equation}
  \mathcal{N}(s) = \text{strip\_synthetic\_roots}\left(\text{replace}(s, \texttt{"\string:\string:"}, \texttt{"."})\right)
\end{equation}

Every extracted vertex $v \in V_{\text{raw}}$ is assigned a standardized component kind $k(v)$. Vertices are partitioned into two disjoint subsets based on their architectural persistence:
\begin{enumerate}
  \item \textbf{Architectural (Non-Volatile) Entities} ($V_{\text{arch}}$): Coarse-grained logical structural containers that define system architecture and module boundaries:
    \begin{equation}
      V_{\text{arch}} = \{ v \in V_{\text{raw}} \mid k(v) \in \mathcal{K}_{\text{arch}} \}
    \end{equation}
    where $\mathcal{K}_{\text{arch}} = \{ \texttt{package}, \texttt{module}, \texttt{class}, \texttt{interface}, \texttt{enum}, \texttt{annotation} \}$.
  \item \textbf{Volatile (Fine-Grained) Entities} ($V_{\text{vol}}$): AST-level sub-components that exist within architectural containers:
    \begin{equation}
      V_{\text{vol}} = \{ v \in V_{\text{raw}} \mid k(v) \in \mathcal{K}_{\text{vol}} \}
    \end{equation}
    where $\mathcal{K}_{\text{vol}} = \{ \texttt{method}, \texttt{function}, \texttt{field}, \texttt{variable}, \texttt{typealias} \}$.
\end{enumerate}

\subsection{The Semantic Entity Lifting Operator}
\label{subsec:semantic_lifting}

To compare fine-grained analyzers (which emit call graphs between individual functions and field accesses) with coarse-grained architectural analyzers (which emit dependency graphs between classes and packages), we introduce the \textbf{Semantic Lifting Operator} $\lambda$.

Let $\text{parent}(v)$ denote the immediate enclosing parent entity of $v$ within the syntactic containment hierarchy of the source code. The lifting function $\lambda : V_{\text{raw}} \to V_{\text{arch}} \cup \{ \bot \}$ recursively projects any vertex to its nearest enclosing non-volatile architectural ancestor:
\begin{equation}
  \lambda(v) = \begin{cases}
    v & \text{if } v \in V_{\text{arch}} \\
    \lambda(\text{parent}(v)) & \text{if } v \in V_{\text{vol}} \text{ and } \text{parent}(v) \neq \bot \\
    \bot & \text{otherwise}
  \end{cases}
\end{equation}

When lifting is applied to dependency edges, it elevates member-level interactions to the architectural component level. Let $e = \langle u, v, \ell \rangle \in E_{\text{raw}}$ be a directed dependency edge with source $u$, target $v$, and label $\ell$. The lifted edge set $E_{\text{lifted}}$ is defined as:
\begin{multline}
  E_{\text{lifted}} = \big\{ \langle \lambda(u), \lambda(v), \tau(\ell) \rangle \;\big|\; \langle u, v, \ell \rangle \in E_{\text{raw}} \;\land \\
  \lambda(u) \neq \bot \;\land\; \lambda(v) \neq \bot \;\land\; \lambda(u) \neq \lambda(v) \big\}
\end{multline}
where $\tau(\ell)$ is the relational taxonomy mapping function defined in Section \ref{subsec:edge_taxonomy_unification}.

Crucially, the condition $\lambda(u) \neq \lambda(v)$ enforces \textbf{intra-component self-loop suppression}: interactions between methods and fields residing within the same class (e.g., private helper method invocations or internal state mutations) collapse to identity and are pruned. This ensures that the evaluation focuses strictly on \textit{inter-component} architectural couplings.

\subsection{Hierarchical Containment Synthesis and Structural Closure}
\label{subsec:structural_closure}

Architectural analysis depends heavily on the hierarchical namespace tree (e.g., detecting package cycles or modular layering violations). However, analyzers differ fundamentally in how they export containment:
\begin{itemize}
  \item Some tools emit only leaf classes (e.g., \texttt{org.example.service.UserService}), leaving the parent packages (\texttt{org.example.service} and \texttt{org.example}) implicit.
  \item Compound graph exporters encode containment via node attributes rather than explicit edges.
\end{itemize}

To guarantee structural closure and fairness, the harmonization framework enforces \textbf{Intermediate Package Synthesis} and \textbf{Explicit Containment Closure}.

For every architectural entity $\pi = \langle \iota_1, \iota_2, \dots, \iota_m \rangle \in V_{\text{arch}}$, the framework synthesizes all intermediate ancestor namespace packages that are absent from the graph:
\begin{equation}
  \text{Prefixes}(\pi) = \{ \langle \iota_1, \dots, \iota_j \rangle \mid 1 \le j < m \}
\end{equation}
\begin{equation}
  V_{\text{arch}}^* = V_{\text{arch}} \cup \bigcup_{\pi \in V_{\text{arch}}} \text{Prefixes}(\pi)
\end{equation}

Subsequently, for every child node $u \in V_{\text{arch}}^*$ possessing a valid structural parent $\text{parent}(u) \in V_{\text{arch}}^*$, an explicit structural containment edge is synthesized:
\begin{equation}
  E_{\text{containment}} = \{ \langle u, \text{parent}(u), \texttt{belongsTo} \rangle \mid u \in V_{\text{arch}}^* \land \text{parent}(u) \neq \bot \}
\end{equation}

This transformation eliminates structural blind spots, allowing compound-based formats (such as Cytoscape JSON) and edge-based formats (such as GraphML) to be compared with complete mathematical equivalence.

\subsection{Unified Relational Taxonomy}
\label{subsec:edge_taxonomy_unification}

To reconcile the proprietary edge labels emitted by diverse analyzers, the framework establishes a surjective mapping $\tau : \mathcal{R}_{\text{tool}} \to \mathcal{R}_{\text{unified}}$ onto five foundational architectural relationship classes:
\begin{equation}
  \mathcal{R}_{\text{unified}} = \left\{ \begin{aligned}
    &\texttt{belongsTo}, \texttt{isChildOf}, \texttt{isImplementationOf}, \\
    &\texttt{includes}, \texttt{dependsOn}
  \end{aligned} \right\}
\end{equation}

\section{Evaluation Metrics and Comparative Formulation}
\label{sec:evaluation_metrics}

With all graphs mapped to canonical, lifted representations $G = (V, E)$, structural concordance and divergence are quantified through set-theoretic and statistical indices.

\subsection{Graph Similarity via Smoothed Jaccard Index}
\label{subsec:jaccard_similarity}

The primary measure of cross-tool structural agreement between two normalized graphs $G_A = (V_A, E_A)$ and $G_B = (V_B, E_B)$ is the \textbf{Jaccard Similarity Index} \cite{ortin_empirical_2022}. To ensure numerical stability when evaluating sparse graphs, submodules with empty edge sets, or boundary components, we employ \textbf{Laplace-smoothed} Jaccard formulations:

\begin{definition}[Smoothed Node Jaccard Similarity]
The structural agreement between the extracted vertex sets $V_A$ and $V_B$ is defined as:
\begin{equation}
  J_{\text{nodes}}(G_A, G_B) = \frac{|V_A \cap V_B| + 1}{|V_A \cup V_B| + 1}
\end{equation}
\end{definition}

\begin{definition}[Smoothed Edge Jaccard Similarity]
Let each edge $e \in E$ be uniquely indexed by the tuple $\langle \text{source}, \text{target} \rangle$ (for unlabelled structural comparison) or $\langle \text{source}, \text{target}, \text{label} \rangle$ (for typed relational comparison). The edge agreement is defined as:
\begin{equation}
  J_{\text{edges}}(G_A, G_B) = \frac{|E_A \cap E_B| + 1}{|E_A \cup E_B| + 1}
\end{equation}
\end{definition}

\noindent
\textbf{Properties of the Metric}:
\begin{itemize}
  \item $J(G_A, G_B) \in (0, 1]$ for all non-empty graphs, reaching $1.0$ if and only if $V_A = V_B$ (or $E_A = E_B$).
  \item In the presence of empty edge sets ($|E_A \cup E_B| = 0$), the smoothed index evaluates to $1.0$, correctly reflecting the agreement that no dependencies exist, rather than producing an undefined $\frac{0}{0}$ indeterminate form.
  \item For realistic codebases where $|V| \gg 1$ and $|E| \gg 1$, the additive Laplace smoothing factor ($+1$) introduces negligible variance while asymptotically converging to standard Jaccard similarity.
\end{itemize}

\subsection{Directional Discrepancy Indices}
\label{subsec:discrepancy_indices}

While the Jaccard index summarizes global bidirectional overlap, it is inherently symmetric: it cannot diagnose \textit{which} tool extracted a richer architectural graph or identify the nature of missing dependencies. To measure directional asymmetry, we define two complementary discrepancy metrics normalized by the shared agreement space:

\begin{definition}[Superiority Index (Relative Novelty)]
The degree to which analyzer $A$ discovers entities or dependencies that are absent in analyzer $B$, relative to their shared intersection, is given by:
\begin{equation}
  \text{Sup}(A, B) = \begin{cases}
    \frac{|A \setminus B|}{|A \cap B|} & \text{if } |A \cap B| > 0 \\
    1.0 & \text{if } |A \cap B| = 0 \text{ and } |A \setminus B| > 0 \\
    0.0 & \text{otherwise}
  \end{cases}
\end{equation}
\end{definition}

\begin{definition}[Inferiority Index (Relative Omission)]
Conversely, the degree to which analyzer $A$ fails to discover entities or dependencies that are successfully extracted by analyzer $B$ is:
\begin{equation}
  \text{Inf}(A, B) = \text{Sup}(B, A) = \begin{cases}
    \frac{|B \setminus A|}{|A \cap B|} & \text{if } |A \cap B| > 0 \\
    1.0 & \text{if } |A \cap B| = 0 \text{ and } |B \setminus A| > 0 \\
    0.0 & \text{otherwise}
  \end{cases}
\end{equation}
\end{definition}

\noindent
These indices provide intuitive diagnostic semantics:
\begin{itemize}
  \item $\text{Sup}(A, B) = 0$ indicates that all elements extracted by $A$ are confirmed by $B$ ($A \subseteq B$).
  \item $\text{Sup}(A, B) = 0.5$ implies that for every two shared dependencies agreed upon by both tools, tool $A$ identifies one additional dependency not seen by $B$.
  \item Comparing $\text{Sup}(\text{OmniDeps}, \text{Baseline})$ against $\text{Inf}(\text{OmniDeps}, \text{Baseline})$ immediately reveals whether OmniDeps behaves conservatively (high precision, lower recall) or aggressively (extracting deeper dependency chains at the risk of over-approximation).
\end{itemize}

\subsection{Categorical Discordance Decomposition}
\label{subsec:categorical_discordance}

To isolate the root causes of architectural divergence, discrepancies must be analyzed per relational type. For each unified relation class $\kappa \in \mathcal{R}_{\text{unified}}$, let $E_A^{(\kappa)} = \{ \langle u, v, \ell \rangle \in E_A \mid \ell = \kappa \}$ denote the partition of edges bearing label $\kappa$.

We compute the \textbf{Relative Discordance Rates}:
\begin{equation}
  \Delta_{A \setminus B}(\kappa) = \frac{|E_A^{(\kappa)} \setminus E_B^{(\kappa)}|}{|E_A^{(\kappa)}|}, \qquad
  \Delta_{B \setminus A}(\kappa) = \frac{|E_B^{(\kappa)} \setminus E_A^{(\kappa)}|}{|E_B^{(\kappa)}|}
\end{equation}

By inspecting $\Delta(\kappa)$ across $\kappa \in \{ \texttt{belongsTo}, \texttt{isChildOf}, \texttt{dependsOn}, \texttt{includes} \}$, the evaluation distinguishes between:
\begin{itemize}
  \item \textbf{Structural Containment Errors} ($\Delta(\texttt{belongsTo}) > 0$): Flaws in package synthesis, namespace path decomposition, or compound node parent lifting.
  \item \textbf{Type Hierarchy Divergences} ($\Delta(\texttt{isChildOf}) > 0$): Failures to resolve base classes, generic bounds, or interface implementations.
  \item \textbf{Behavioral Call Resolution Divergences} ($\Delta(\texttt{dependsOn}) > 0$): Differences in call-graph construction, member-to-class attachment, or type inference on local variables.
\end{itemize}

\subsection{Endpoint-Conditioned Edge Precision}
\label{subsec:endpoint_conditioned_precision}

When tool $A$ emits an edge $e = \langle u, v \rangle$ that is absent in tool $B$, the discrepancy can stem from two completely distinct operational failures:
\begin{enumerate}
  \item \textbf{Syntactic Parsing Gap}: Tool $B$ failed to extract node $u$ or node $v$ in the first place (e.g., due to an unsupported grammar construct or file discovery filter).
  \item \textbf{Semantic Resolution Gap}: Both tools successfully identified nodes $u$ and $v$, but tool $B$ failed to establish the semantic dependency linking them.
\end{enumerate}

To decouple resolution accuracy from syntactic node discovery, we define the \textbf{Endpoint-Conditioned Edge Set} $E_{A \mid V_B}$:
\begin{equation}
  E_{A \mid V_B} = \{ \langle u, v, \ell \rangle \in E_A \mid u \in V_B \;\land\; v \in V_B \}
\end{equation}

Evaluating edge similarity conditioned on shared vertices ($E_{A \mid V_B}$ versus $E_{B \mid V_A}$) isolates the name resolution engine's ability to resolve valid linkages from external factors such as compiler front-end preprocessor flags or file exclusion heuristics.

\section{Experimental Design and Benchmark Corpus}
\label{sec:experimental_design}

To ensure comprehensive empirical validation, the evaluation methodology couples controlled micro-benchmarks with a multi-language dataset of real-world software systems.

\subsection{Controlled Micro-Benchmarks and Ground-Truth Oracles}
\label{subsec:micro_benchmarks}

To answer \textbf{RQ1}, absolute ground-truth oracles were constructed for each of the five target languages (C, C++, Java, Rust, and Python). Unlike large production repositories where a complete, verified ground truth is unattainable, micro-benchmarks are purposefully engineered to exercise specific language idioms and edge cases in isolation.

For each micro-benchmark, a formal architectural oracle $\mathcal{O} = \langle V^*, E^* \rangle$ is hand-crafted and verified through manual static analysis:
\begin{itemize}
  \item \textbf{C Benchmark}: Evaluates structural file coupling via header inclusions (\texttt{\#include}), type definitions (\texttt{typedef struct}), function pointers, opaque pointer patterns, and nested struct definitions.
  \item \textbf{C++ Benchmark}: Exercises class templates (\texttt{template<typename T>}), specialized member functions, out-of-line method definitions across translation units, virtual and multiple inheritance, and namespace aliases.
  \item \textbf{Java Benchmark}: Evaluates bounded type parameters (\texttt{<T extends Comparable<T>>}), interface realization, deeply nested inner classes, static factory methods, and cross-package package-private access.
  \item \textbf{Rust Benchmark}: Focuses on algebraic data types (\texttt{enum} with payload variants), trait definitions, generic \texttt{impl<T> Trait for Struct<T>} blocks, associated types, and decoupled re-exports via \texttt{pub use}.
  \item \textbf{Python Benchmark}: Assesses dynamic duck-typing, \texttt{typing.Generic} and \texttt{TypeVar} annotations, module-level variable definitions, relative package imports (\texttt{from ..pkg import mod}), and factory call instantiations.
\end{itemize}

Extraction accuracy against the ground-truth oracle $\mathcal{O} = \langle V^*, E^* \rangle$ is evaluated using standard Information Retrieval metrics:
\begin{gather}
  \text{Precision}_{\text{edges}} = \frac{|E_{\text{ext}} \cap E^*|}{|E_{\text{ext}}|}, \qquad
  \text{Recall}_{\text{edges}} = \frac{|E_{\text{ext}} \cap E^*|}{|E^*|}, \\
  F_1 = \frac{2 \cdot \text{Precision}_{\text{edges}} \cdot \text{Recall}_{\text{edges}}}{\text{Precision}_{\text{edges}} + \text{Recall}_{\text{edges}}}
\end{gather}

\subsection{Comparator Baseline Analyzers}
\label{subsec:baseline_analyzers}

OmniDeps is benchmarked against three state-of-the-art static analysis tools, selected to contrast different parsing and extraction philosophies:
\begin{enumerate}
  \item \textbf{Arcan} \cite{fontana_arcan_2017}: An architectural analysis framework and architectural smell detector. Arcan relies on compiler-based front-ends (Spoon for Java, Clang AST for C/C++), providing deep semantic understanding of types at the cost of language coupling and high runtime overhead.
  \item \textbf{Depends} \cite{depends_github}: A state-of-the-art multi-language dependency analyzer. Depends employs ANTLR-generated grammar parsers for C/C++, Java, and Python, emitting Dependency Structure Matrices (DSM) and fine-grained call/use dependencies.
  \item \textbf{Entangle} \cite{teruzzi_2024}: A direct predecessor research prototype developed within our laboratory. Entangle abandoned compiler front-ends in favor of Tree-sitter AST parsing and dynamic scope climbing for C and Java, serving as an architectural baseline for AST-based heuristics.
\end{enumerate}

\section{Runtime Performance and Scalability Benchmarking Protocol}
\label{sec:benchmarking_protocol}

To rigorously answer \textbf{RQ4}, a disciplined experimental benchmarking protocol was formulated to measure execution time, scalability, and computational throughput.

\subsection{Experimental Rigor and Execution Sampling}
\label{subsec:execution_sampling}

Because external processes are subject to operating system scheduling noise, cache warmup variations, and memory allocation jitter, raw single-run execution times are statistically unreliable. The benchmarking framework enforces the following execution protocol:
\begin{enumerate}
  \item \textbf{Multi-Iteration Sampling}: Every tool is executed over $k$ independent iterations ($k \ge 10$ for runtime benchmarking, $k = 1$ for structural deliverable extraction). For each project and tool, the sample mean execution time $\mu$ and standard deviation $\sigma$ are calculated:
    \begin{equation}
      \mu = \frac{1}{k} \sum_{i=1}^k t_i, \qquad \sigma = \sqrt{\frac{1}{k - 1} \sum_{i=1}^k (t_i - \mu)^2}
    \end{equation}
  \item \textbf{Hardware and OS Isolation}: On supported platforms, the benchmarking harness pins execution to a dedicated physical CPU core (e.g., via affinity masks) to eliminate context switching, thread migration, and scheduler jitter.
  \item \textbf{Process Group Isolation and Cleanup}: Analyzers frequently spawn child sub-processes (such as JVM worker threads or compiler subshells). Benchmark processes are instantiated within isolated POSIX sessions (\texttt{setsid}). In the event of process failure, abnormal exit, or timeout expiration, the entire process group is cleanly terminated via $\texttt{SIGKILL}$, preventing orphaned background processes from corrupting subsequent measurements.
  \item \textbf{Configurable Execution Timeouts}: When analyzing large codebases, complex macro expansions or cyclic grammar constructs can induce pathological backtracking loops in baseline tools. A configurable timeout $T_{\text{max}}$ (e.g., 30 minutes) is enforced. Runs exceeding $T_{\text{max}}$ are recorded as timeouts without stalling batch benchmark execution.
\end{enumerate}

\subsection{Scalability and Throughput Metrics}
\label{subsec:scalability_metrics}

Scalability is evaluated across two primary dimensions:
\begin{itemize}
  \item \textbf{Analysis Throughput} ($\Theta$): The processing speed measured in source lines of code analyzed per unit of wall-clock time:
    \begin{equation}
      \Theta = \frac{\text{CLOC}}{\mu_t} \quad \left[\frac{\text{lines}}{\text{second}}\right]
    \end{equation}
  \item \textbf{Relative Speedup} ($S$): The execution speedup achieved by OmniDeps relative to comparator baseline $B$:
    \begin{equation}
      S_{B} = \frac{\mu_{t, B}}{\mu_{t, \text{OmniDeps}}}
    \end{equation}
    where $S_B > 1.0$ indicates superior performance by OmniDeps.
\end{itemize}

\section{Threats to Validity}
\label{sec:threats_to_validity}

To ensure sound interpretation of the experimental outcomes, potential threats to validity must be recognized and systematically mitigated across three methodological dimensions: construct, internal, and external validity.

\subsection{Construct Validity}
\label{subsec:construct_validity}

Threats to construct validity concern whether the operationalized evaluation metrics and graph transformations truly reflect architectural dependency extraction fidelity rather than superficial artifacts of representation.

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Metamodel Harmonization and Semantic Lifting}: Divergent static analysis tools represent software structure at fundamentally different granularities. A fine-grained tool such as \textit{Depends} captures AST-level function calls and local field references, whereas architectural smell detectors such as \textit{Arcan} extract class-to-class and package-level couplings. We mitigated this disparity through the formal Semantic Lifting Operator ($\lambda$, Section~\ref{subsec:semantic_lifting}), which lifts member-level interactions to enclosing architectural types ($V_{\text{arch}}$) and suppresses intra-component self-loops. Furthermore, we defined Intermediate Package Synthesis and Explicit Containment Closure (Section~\ref{subsec:structural_closure}) to eliminate artificial penalization arising from compound node nesting versus explicit containment edges.
  
  \item \textbf{Ontological Granularity Gaps in Procedural Codebases}: In procedural languages (C and C++), analyzers may model architecture at the level of physical translation units (file-to-file graphs) rather than user-defined data structures (type-to-type graphs). As analyzed in Section~\ref{subsubsec:arcan_c_cpp_divergence}, comparing Arcan's file-level graphs with OmniDeps' type-centric graphs yields disjoint vertex spaces ($V_{\text{Arcan}} \cap V_{\text{OmniDeps}} = \emptyset$). Rather than reporting artificially deflated zero scores, we identified this as an ontological mismatch and explicitly marked Arcan as non-comparable for C and C++, preserving metric construct integrity.

  \item \textbf{Metric Sensitivity and Smoothing}: Graph similarity is evaluated using the Laplace-smoothed Jaccard index ($J_{\text{nodes}}$ and $J_{\text{edges}}$, Section~\ref{subsec:jaccard_similarity}). For sparse submodules or repositories where no subtype edges exist, Laplace smoothing prevents indeterminate forms ($\frac{0}{0}$) without biasing results on large-scale systems where $|V| \gg 1$ and $|E| \gg 1$. In addition, directional superiority ($\text{Sup}$) and inferiority ($\text{Inf}$) indices (Section~\ref{subsec:discrepancy_indices}) ensure that asymmetric over-approximation and omission are quantified independently.
\end{itemize}

\subsection{Internal Validity}
\label{subsec:internal_validity}

Threats to internal validity concern potential confounding factors in the experimental implementation, preprocessing pipeline, or measurement execution.

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Translation-Unit Preprocessing and Header Inlining}: In procedural and object-oriented C/C++, macro expansion and header file inclusion represent a critical trade-off. In raw source files, unexpanded conditional macros and missing \texttt{\#include} paths cause unlinked types and unresolved function invocations. To evaluate the impact of compiler preprocessing, we implemented an automated translation-unit (TU) preprocessor invoking \texttt{clang -E} (filtering system headers from \texttt{/usr/include}). While TU preprocessing eliminates unlinked macros and increases node recall (reducing $\text{Inf}_{\text{nodes}}$ to $\approx 0.05$--$0.15$ on key projects), inlining shared header files duplicates type definitions across every translation unit that includes them, inflating apparent node superiority ($\text{Sup}_{\text{nodes}}$). Conversely, post-preprocessing stripping of inlined headers via compiler linemarkers breaks compiler-based frontends (such as Eclipse CDT in Depends), which require complete type definitions within each compilation unit to resolve symbols. Consequently, we report both raw and preprocessed results to isolate the impact of header inlining.

  \item \textbf{Dynamic Features and Reflection}: In dynamically typed languages like Python, static analysis inherently cannot observe runtime reflection, dynamic dispatch via \texttt{getattr}, or runtime monkey-patching. This creates an expected ceiling on edge recall in dynamic languages, as static AST queries cannot infer types that exist solely during interpreter runtime.

  \item \textbf{Benchmarking and Execution Measurement Rigor}: Comparing native compiled binaries (written in Rust) against JVM-based analyzers (Arcan and Depends) introduces potential execution bias due to JVM bytecode warmup, Just-In-Time (JIT) compilation, and garbage collection pauses. To mitigate runtime variance, each benchmark iteration was executed within isolated POSIX process sessions (\texttt{setsid}) with clean subprocess tree termination via $\texttt{SIGKILL}$, CPU affinity pinning, and a hard timeout ($T_{\text{max}} = 30$ minutes). Timings were captured across repeated sampling iterations, separating process startup from steady-state execution.
\end{itemize}

\subsection{External Validity}
\label{subsec:external_validity}

Threats to external validity concern the generalizability of our findings across diverse software ecosystems, paradigms, and programming languages.

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Corpus Scale and Heterogeneity}: To avoid conclusions biased toward specific project structures, our empirical evaluation dataset encompasses 156 open-source software projects spanning five distinct languages (31 C, 31 C++, 32 Java, 30 Python, and 32 Rust repositories) and aggregating over 45 million lines of code.

  \item \textbf{Architectural and Domain Diversity}: The evaluated corpus includes low-level systems and operating systems tooling (\texttt{git}, \texttt{tmux}, \texttt{libuv}), high-throughput databases and storage engines (\texttt{redis}, \texttt{sqlite}, \texttt{ClickHouse}, \texttt{duckdb}), distributed enterprise platforms (\texttt{elasticsearch}, \texttt{flink}), game engines (\texttt{godot}), networking microframeworks (\texttt{fastapi}, \texttt{flask}, \texttt{actix-web}), and developer toolchains (\texttt{ripgrep}, \texttt{cargo}, \texttt{ninja}). This breadth ensures that evaluation results reflect real-world engineering diversity rather than narrow domain-specific idioms.
\end{itemize}

\subsubsection{Ontological Granularity Divergence in C/C++: Arcan vs. OmniDeps}
\label{subsubsec:arcan_c_cpp_divergence}

A critical empirical and methodological finding emerging from the cross-tool evaluation concerns the structural comparison between OmniDeps and Arcan on C and C++ repositories. While in Java OmniDeps and Arcan exhibit high mutual concordance ($J_{\text{nodes}} \in [0.50, 0.86]$ and $J_{\text{edges}} \in [0.45, 0.80]$), direct graph alignment between the two tools on C and C++ yields an effective Jaccard similarity of virtually zero ($J_{\text{nodes}} \approx 0.000$, $J_{\text{edges}} \approx 0.000$).

A deep inspection of the raw graph deliverables reveals that this divergence does not stem from parsing errors or extraction defects, but rather from a fundamental \textbf{ontological discrepancy in architectural modeling across programming paradigms}:
\begin{enumerate}
    \item \textbf{Object-Oriented Parity in Java}: In Java, all evaluated tools (OmniDeps, Depends, and Arcan) share a unified, class-centric metamodel. Arcan's Java frontend extracts object-oriented entities (\texttt{CONCRETE\_CLASS}, \texttt{ABSTRACT\_CLASS}, \texttt{INTERFACE}, \texttt{PACKAGE}, and \texttt{ENUM}), which map directly to OmniDeps' architectural entities ($V_{\text{arch}}$). Under this shared ontology, semantic lifting operates seamlessly, yielding strong structural and topological alignment.
    
    \item \textbf{Compilation-Unit vs. Type-Level Models in C and C++}: In procedural and multi-paradigm languages such as C and C++, modular containers are not formally enforced by language-level package constructs. As a result, the tools adopt divergent levels of abstraction:
    \begin{itemize}
        \item \textbf{Arcan (File-Level / Translation-Unit Graph)}: Arcan's C/C++ analyzer targets architectural smell detection (e.g., cyclic dependencies and hub-like components) by modeling systems strictly at the level of physical translation units. The vertices in Arcan's C/C++ graph are exclusively source implementation files (\texttt{IMPL\_FILE}, e.g., \texttt{hostip6.c}), header files (\texttt{HEADER}, e.g., \texttt{sockaddr.h}), and directory packages (\texttt{COMPONENT}, e.g., \texttt{curl.lib.vdns}). Arcan \textit{never extracts user-defined types} (structs, unions, classes), functions, or methods as distinct graph vertices. Inter-file function calls and variable references are aggregated into file-to-file $\texttt{dependsOn}$ edges, while $\texttt{\#include}$ directives are modeled as $\texttt{includes}$ edges.
        \item \textbf{OmniDeps and Depends (Type-Centric Structural Graph)}: Conversely, both OmniDeps and Depends model C and C++ at the level of data structures and types. Their non-volatile vertices consist of $\texttt{struct}$, $\texttt{class}$, $\texttt{union}$, and $\texttt{enum}$ definitions (e.g., \texttt{struct stat}, \texttt{struct Curl\_easy}, \texttt{class Builder}). In accordance with the harmonization framework (Section~\ref{sec:graph_harmonization_framework}), free functions and local variables are either lifted into their enclosing structured types or discarded.
    \end{itemize}
\end{enumerate}

Consequently, when evaluating graph intersection under the canonical hash operator ($\text{hash}(v) = \text{id}(v)$), the set of file-path vertices emitted by Arcan:
\begin{equation}
    V_{\text{Arcan}} = \{ \texttt{hostip6.c}, \texttt{sockaddr.h}, \texttt{multi.c}, \dots \}
\end{equation}
and the set of struct/class identifiers emitted by OmniDeps:
\begin{equation}
    V_{\text{OmniDeps}} = \{ \texttt{Curl\_easy}, \texttt{hostent}, \texttt{stat}, \dots \}
\end{equation}
are completely disjoint ($V_{\text{Arcan}} \cap V_{\text{OmniDeps}} = \emptyset$), rendering the two representations mathematically orthogonal.

Additionally, a secondary impedance mismatch was identified during adapter construction: naive splitting of identifiers on the dot separator (\texttt{"."})---appropriate for Java qualified package names like \texttt{org.antlr.v4.Tool}---mistakenly treats C/C++ file extensions as type names (e.g., converting \texttt{hostip6.c} into an entity \texttt{"c"} belonging to a synthetic package \texttt{"hostip6"}). However, even when adjusting for filename extensions, the underlying graph data remains fundamentally non-isomorphic.

\textbf{Methodological Implication}: For the purpose of fair and objective cross-tool benchmarking, Arcan is marked as non-comparable (\texttt{---}) for C and C++ in Table~\ref{tab:pairwise_jaccard_summary}. This empirical finding highlights an important conceptual lesson for static analysis research: architectural smell detection tools often trade typological fidelity for file-level aggregation when analyzing procedural systems, creating an unbridgeable semantic gap when contrasted with type-level dependency analyzers.

  \item \textbf{Near-Perfect Containment Agreement (\texttt{belongsTo})}: OmniDeps exhibits extraordinary structural fidelity with baseline tools on package and class hierarchy. Omission rates are negligible: Depends contains only \textbf{1.8\%} of containment edges not found by OmniDeps ($\Delta_{B \setminus A} = 0.018$, with a median of just 0.4\%), and Arcan contains only \textbf{0.3\%} ($\Delta_{B \setminus A} = 0.003$).   \item \textbf{Subtype and Interface Realization Hierarchies}: When evaluating inheritance and contracts (\texttt{isChildOf} and \texttt{isImplementationOf}), OmniDeps recovers \textbf{91.3\%} of Depends' edges ($\Delta_{B \setminus A} = 8.7\%$) and \textbf{97.6\%} of Arcan's edges ($\Delta_{B \setminus A} = 2.4\%$). The discrepancy in $\texttt{isImplementationOf}$ reflects an ontological taxonomy choice: Arcan strictly segregates class extension (\texttt{extend}) into $\texttt{isChildOf}$ and interface contract realization (\texttt{implement}) into $\texttt{isImplementationOf}$ (averaging 702 edges per project). Conversely, both OmniDeps and Depends unify type hierarchy edges under generalized subtyping ($\texttt{isChildOf}$), resulting in zero direct $\texttt{isImplementationOf}$ matches but complete subtyping capture.

  \item \textbf{Symmetric Behavioral Coupling Concordance (\texttt{dependsOn})}: On behavioral and call-graph dependencies, OmniDeps and Depends exhibit an average intersection of \textbf{27,891 shared edges per project}. Remarkably, their discordance rates are perfectly symmetric: $\Delta_{A \setminus B} = \mathbf{26.1\%}$ and $\Delta_{B \setminus A} = \mathbf{26.1\%}$. Detailed inspection shows that OmniDeps captures field-level type references and constructor instantiations that Depends misses, while Depends (utilizing a multi-pass AST symbol table) resolves chained method calls and statically imported member invocations that OmniDeps abstracts over during single-pass CST query matching.

  \item \textbf{Import Directives (\texttt{includes})}: In Java, Arcan strips file-level \texttt{import} statements entirely ($\Delta_{B \setminus A} = 0$, $|B| = 0$), modeling only semantic type usages. Depends exports imports under file-level nodes, which, upon semantic lifting to enclosing classes, map to package-level or class-level inclusions.
\end{enumerate}

\subsubsection{C/C++ Header Inlining vs. Incomplete Type Requirements}
In procedural C and C++, typological discordance is governed by header file semantics. When translation units are preprocessed via \texttt{clang -E}, header files are inlined into every including compilation unit. Consequently, any data structure declared in a shared header (e.g., \texttt{struct sockaddr} in \texttt{sys/socket.h} or \texttt{struct Buffer} in an internal header) is parsed and instantiated as an AST node in every translation unit that includes it. This multiplies the apparent vertex count in Tree-sitter, increasing node superiority ($\text{Sup}_{\text{nodes}}$).

To test whether this duplication could be eliminated, we investigated stripping inlined header lines based on preprocessor linemarkers (\texttt{\# 1 "header.h"}). However, this experiment revealed an important architectural insight: compiler-based static analysis frontends (such as Eclipse CDT in Depends) require complete type definitions within each compilation unit to perform symbol resolution. Stripping header contents produced incomplete type syntax errors, causing Depends to fail on compilation units and collapsing graph intersections to zero on projects like \texttt{curl} and \texttt{nginx}. Thus, translation-unit preprocessing without an external cross-TU linker represents an unavoidable trade-off between type visibility and vertex duplication in single-pass analyzers.

\subsubsection{Architectural Drivers of OmniDeps' Performance Advantage}
The substantial throughput and speedup gains achieved by OmniDeps stem from three fundamental architectural decisions:
\begin{enumerate}
  \item \textbf{Parallel CST Traversal with Rayon}: Rather than parsing files sequentially or relying on coarse-grained process pools, OmniDeps utilizes Rust's work-stealing thread pool (\texttt{rayon}) to parse individual source files in parallel. Because Tree-sitter parsers are re-entrant and operate entirely in native memory, parallel file extraction scales linearly across available CPU cores without Global Interpreter Lock (GIL) contention or thread synchronization bottlenecks.
  
  \item \textbf{Arena-Allocated Universal Intermediate Representation}: Baseline tools implemented in Java (Arcan, Depends) allocate millions of individual heap objects during AST construction, triggering significant JVM garbage collection overhead. In contrast, OmniDeps employs arena allocation and contiguous vector storage for its Universal IR, minimizing heap allocations, eliminating cache misses, and avoiding pointer chasing.
  
  \item \textbf{Declarative Query Algebra vs. Multi-Pass AST Visitors}: Tools like Depends perform multiple recursive passes over the complete AST to resolve types and references. OmniDeps executes Tree-sitter query patterns compiled into byte-code sentinels in a single linear pass over the concrete syntax tree, minimizing algorithmic complexity and memory footprint.
\end{enumerate}
