\section{Future Work}
\label{ch:future_work}

The work presented in this thesis establishes a scalable and language-agnostic
framework for architectural dependency extraction. By abstracting extraction
logic through syntax-directed queries on Concrete Syntax Trees (CSTs) and
formalizing a flexible Intermediate Representation ($\mathcal{D}_{IR}$), the
system addresses the configuration and scalability bottlenecks of traditional
compiler-coupled front-ends. The empirical evaluation demonstrated the
practical viability of the approach across five programming languages,
resolving nested scopes, qualified paths, and cross-module dependencies.

However, because the primary focus of this research was the conceptualization,
formalization, and empirical validation of the intermediate representation model
and extraction heuristics, several avenues remain open for future research.
The following subsections outline the primary directions for future work.

\subsection{Performance and Concurrency Optimizations}
\label{subsec:future_performance}

Throughout the development of this thesis, the primary objective was ensuring
the correctness, sound formalization, and baseline algorithmic
scalability of the
intermediate representation and algebraic query engine. Consequently, minimal
effort was directed toward low-level execution tuning, and the current research
prototype operates sequentially. While the algorithmic complexity remains well
bounded—sustaining high throughput on modern hardware—real-world continuous
integration (CI) pipelines and large enterprise monorepos can benefit from
explicit concurrency.

Future iterations of the framework can introduce parallelism at multiple stages:
\begin{itemize}
  \item \textbf{Data-Parallel Syntactic Extraction}: The extraction
    phase (Phase 1)
    is embarrassingly parallel, as Tree-sitter parsing and CST
    traversal operate on
    individual source files without requiring mutable shared state.
    Processing files
    concurrently across available CPU cores (for instance, via a
      work-stealing thread
    pool such as Rust's \texttt{rayon}) would scale extraction throughput almost
    linearly with core count, bounded primarily by disk I/O.
  \item \textbf{Concurrent Query Resolution}: In the resolution phase (Phase 2),
    evaluating self-contained queries against the global Scope Tree presents
    opportunities for read-concurrency. Independent symbol queries
    originating from
    different function bodies can be evaluated in parallel using concurrent data
    structures or fine-grained reader-writer locks (\texttt{RwLock}),
    while batching
    graph vertex and edge insertions to minimize contention.
\end{itemize}

\subsection{Inter-Language Dependency Detection}
\label{subsec:future_inter_language}

Currently, while OmniDeps parses multi-language repositories into a unified
intermediate representation within a single workspace, dependency resolution
remains confined within each language's individual boundaries. For
example, a native
Java method call is recorded as an external reference, but it is not
linked to its
corresponding C or C++ implementation.

In modern systems, cross-language interactions are ubiquitous. A
compelling future
direction is extending the resolution engine with bridging heuristics capable of
identifying and resolving these \textbf{inter-language dependencies}:
\begin{itemize}
  \item \textbf{Foreign Function Interfaces (FFI)}: For conventions such as the
    Java Native Interface (JNI), the framework could identify \texttt{native}
    declarations, compute their standard C/C++ mangled symbols (e.g.,
      following the
    \texttt{Java\_Package\_Class\_Method} scheme), and resolve the
    link directly to
    the matching C/C++ definition in the workspace. Similar bridging
    logic can be
    applied to Rust-Python bindings via PyO3 or C foreign function
    calls in Python.
  \item \textbf{Interface Definition Languages (IDLs)}: In
    distributed architectures
    communicating via Remote Procedure Calls (such as gRPC Protocol
      Buffers or OpenAPI
    specifications), extracting interface schemas would allow the
    analyzer to use the
    IDL contract as an architectural bridge, linking services implemented in
    different languages (e.g., a Go server and a Python client) into a coherent,
    end-to-end dependency graph.
\end{itemize}

\subsection{Alternative Programming Paradigms}
\label{subsec:future_paradigms}

The design and empirical validation of OmniDeps have thus far focused on
procedural and object-oriented languages within the broader C-family
(C, C++, Java,
Python, and Rust). These languages share foundational architectural
concepts, such
as explicit file and package modules, structured types (classes,
structs, interfaces),
and identifiable function or method declarations.

Although the Intermediate Representation ($\mathcal{D}_{IR}$) was designed to be
language-agnostic, extending it to support non-imperative paradigms represents a
meaningful research opportunity:
\begin{itemize}
  \item \textbf{Functional Languages}: In languages such as Haskell, OCaml, or
    Clojure, software architecture relies heavily on higher-order functions,
    currying, closures, and algebraic module systems (e.g., ML
    functors). Capturing
    architectural coupling in these ecosystems will require refining the query
    algebra to track function composition and lexical binding without relying on
    class-like encapsulation.
  \item \textbf{Declarative and Logic Paradigms}: In declarative systems (such as SQL
    transformations or Prolog rule bases), dependencies manifest as relational
    derivations and predicate unification rather than procedural call hierarchies.
    Expanding the relational taxonomy to represent declarative data-flow and rule
    dependencies would further broaden the applicability of the framework.
\end{itemize}

\subsection{Analysis Engine and Modeling Refinements}
\label{subsec:future_engine_refinements}

Beyond scalability and cross-language boundaries, several architectural refinements
to the extraction and resolution algorithms warrant future investigation:
\begin{itemize}
  \item \textbf{Automated Discovery of Primitive Types}: OmniDeps currently maintains
    explicit per-language catalogs to identify built-in and primitive types (e.g.,
    \texttt{int}, \texttt{size\_t}, \texttt{i32}) and synthesize terminal
    \texttt{Primitive} endpoints. Future work could explore automated primitive type
    identification—such as statistical frequency heuristics across AST type nodes or
    automated scraping of language specification headers—eliminating the need for
    manual list configuration when onboarding new languages.
  \item \textbf{Unified Receiver Feature Modeling}: The handling of object-oriented
    receivers (such as explicit keywords \texttt{this} and \texttt{self}, Python's
    positional first parameter, or languages without implicit receiver binding) is
    currently parameterized across separate configuration flags. Future versions can
    formalize this as a unified three-state language feature (\texttt{Keyword},
    \texttt{FirstParam}, or \texttt{None}), simplifying configuration schemas and
    intermediate serialization.
  \item \textbf{Early Query Resolution for Superclasses}: Currently, resolving calls
    delegated via \texttt{super} or \texttt{Self} is executed entirely during Phase~2
    against the global Scope Tree. An optimization avenue involves pre-resolving
    direct superclass bindings during Phase~1 (query building), rewriting \texttt{super}
    invocations into scoped queries before global execution to reduce query traversal
    depth.
  \item \textbf{Link-Time Symbol Deduplication for C and C++}: When analyzing
    preprocessed translation units in procedural C and C++, types declared in shared
    headers are replicated across compilation units. Future iterations should introduce
    an intermediate deduplication layer analogous to a systems linker: identifying
    struct and class declarations with matching signatures originating from shared
    headers, and consolidating them into unified logical nodes in the Scope Tree.
    This would eliminate node inflation artifacts and align graph density with
    compiler-based tools without requiring build-system coupling.
\end{itemize}
