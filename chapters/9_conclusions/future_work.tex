\section{Future Work}
\label{ch:future_work}

While the primary focus of this thesis was the formalization and empirical
validation of the intermediate representation, extraction heuristics, and
resolution pipeline, the modular architecture of OmniDeps opens several avenues
for future research and engineering extensions. The remainder of this section
outlines the primary directions for future work.

\subsubsection{Performance and Concurrency Optimizations}
\label{subsec:future_performance}

Throughout the development of this thesis, the primary objective was ensuring
the correctness, sound formalization, and baseline algorithmic scalability of
the intermediate representation and analysis pipeline. While the algorithmic
complexity remains well bounded, sustaining high throughput on modern hardware,
large-scale enterprise monorepos and continuous integration pipelines can
benefit from deeper concurrency across all stages of the pipeline.

Currently, OmniDeps exploits data-parallelism during both syntactic extraction,
where source files are parsed concurrently across CPU cores, and graph
synthesis, where dependency edges are extracted and deduplicated in parallel
across workspace modules. However, the intermediate name resolution phase still
executes sequentially on a single thread.

Future iterations of the framework can extend multi-core parallelism to the two
sub-stages of name resolution:
\begin{itemize}
  \item \textbf{Parallel Query Building}: During lexical substitution, the
    resolver currently traverses modules sequentially using a single shared
    symbol stack. Because lexical scope substitution within a top-level
    compilation unit is independent of sibling modules, maintaining an isolated
    symbol stack per module would allow query construction to execute in
    parallel across the module hierarchy.
  \item \textbf{Concurrent Query Execution}: During global query evaluation,
    all queries inspect a read-only global Scope Tree and a static primitive
    registry, while sharing a mutable cache of resolved inheritance
    hierarchies. Pre-computing superclass scope mappings during Scope Tree
    construction, or adopting a concurrent caching strategy, would allow
    independent queries to be evaluated in parallel across all modules.
\end{itemize}

\subsubsection{Alternative Programming Paradigms}
\label{subsec:future_paradigms}

The design and empirical validation of OmniDeps have thus far focused on
procedural and object-oriented languages. These languages share
foundational architectural concepts, such as explicit file and
package modules, structured types, and identifiable function or
method declarations.

Although the Intermediate Representation was designed to be language-agnostic,
extending it to support non-imperative paradigms represents a meaningful
research opportunity:
\begin{itemize}
  \item \textbf{Functional Languages}: In functional languages such as Haskell,
    OCaml, or Clojure, software architecture relies heavily on higher-order
    functions, currying, closures, and algebraic module systems. Capturing
    architectural coupling in these ecosystems will require refining the query
    algebra to track function composition and lexical binding without relying
    on class-like encapsulation.
  \item \textbf{Declarative and Logic Paradigms}: In declarative systems such
    as SQL transformations or Prolog rule bases, dependencies manifest as
    relational derivations and predicate unification rather than procedural
    call hierarchies. Expanding the relational taxonomy to represent
    declarative data-flow and rule dependencies would further broaden the
    applicability of the framework.
\end{itemize}

\subsubsection{Analysis Engine and Modeling Refinements}
\label{subsec:future_engine_refinements}

Beyond concurrency and paradigm extensions, several architectural refinements
to the extraction and resolution algorithms warrant future investigation:
\begin{itemize}
  \item \textbf{Automated Discovery of Primitive Types}: OmniDeps currently
    maintains explicit per-language catalogs to identify built-in and primitive
    types and synthesize terminal primitive endpoints. Future work could
    explore automated primitive type identification through statistical
    frequency heuristics across syntax nodes or automated scraping of language
    specification headers, eliminating the need for manual list configuration
    when onboarding new languages.
  \item \textbf{Early Query Resolution for Superclasses}: Currently, resolving
    calls delegated to a superclass is executed entirely during the global
    query evaluation stage against the Scope Tree. An optimization avenue
    involves pre-resolving direct superclass bindings during the query building
    stage, rewriting superclass invocations into scoped queries before global
    execution to reduce query traversal depth.
  \item \textbf{Link-Time Symbol Deduplication for C and C++}: When analyzing
    preprocessed translation units in procedural C and C++, types declared in
    shared headers are replicated across compilation units. Future iterations
    should introduce an intermediate deduplication layer analogous to a systems
    linker: identifying struct and class declarations with matching signatures
    originating from shared headers, and consolidating them into unified
    logical nodes in the Scope Tree. This would eliminate node inflation
    artifacts and align graph density with compiler-based tools without
    requiring build-system coupling.
  \item \textbf{Simplified Self-Reference Configuration}: In the current
    configuration schema, how a language refers to the current instance inside
    a method is split across separate settings: one for fixed keywords such as
    \texttt{this} or \texttt{self}, and another for conventions where the
    instance is passed as the first method parameter, as in Python. Since these
    mechanisms are mutually exclusive, they can be consolidated into a single
    configuration setting.
\end{itemize}

\subsubsection{Inter-Language Dependency Detection}
\label{subsec:future_inter_language}

Finally, a more speculative direction emerged as a reflection on
the architecture of the framework. Although cross-language interaction was
never investigated or addressed during the course of this thesis, the fact that
OmniDeps already projects source files written in different programming
languages into a single intermediate representation and shared Scope Tree
suggests an intriguing long-term research opportunity.

Currently, even when analyzing polyglot repositories, dependency resolution
remains strictly confined within the boundaries of each individual language,
meaning that calls crossing language boundaries are treated simply as unresolved
external references. Future research could explore whether lightweight bridging
heuristics can be layered on top of the unified representation to connect
definitions and references across different languages. Such bridges could, for
instance, link Foreign Function Interface calls such as the Java Native
Interface or Python native bindings to their underlying C, C++, or Rust
implementations, or connect distributed services through shared Remote Procedure
Call and Interface Definition Language schemas.
